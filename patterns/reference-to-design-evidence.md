# Reference-to-Design Evidence

## Purpose
Use repositories, demos, screenshots and social references as useful design/engineering inputs without allowing imitation to replace product reasoning.

## Flow
`Reference → classify → extract candidate principle/pattern → verify if technical claim → map to user/problem → prototype/experiment if uncertain → validate → adopt/reject → evidence`

## Classification
1. Visual inspiration
2. Interaction reference
3. Functional/domain pattern
4. Technical implementation pattern
5. Tool/component candidate
6. Verified reusable engineering evidence

## Rules
- Appearance alone never establishes usability.
- Demo behavior alone never establishes scalability/security/accessibility.
- A source-backed technical pattern still requires fit assessment.
- Product requirements originate from outcomes/domain/user needs, not references.
- If a reference causes a design decision, record what was adopted and why rather than copying the artifact wholesale.
- AI may synthesize alternatives from references but must preserve provenance and distinguish inspiration from verified facts.

## VECTOR pilot question
Can the framework use accumulated repositories to improve interaction/visual/technical quality while still producing a design derived from VECTOR's own capabilities and users?
